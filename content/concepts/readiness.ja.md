# Pod の Ready はプロダクトの Ready ではない

Readiness は単一の普遍的な真偽値ではなく、複数の主張の集合です。自分の証拠がどの主張を証明し、どの主張を証明しないのかを明示してください。

| 主張 | 有用な証拠 | その証拠では確立されないこと |
| --- | --- | --- |
| 意図が受理された | 現行 generation の admission/graph condition | 配送または利用可能性 |
| 配送が完了した | 正確なリリース/ロールアウトの同一性と終端結果 | データプレーンが機能していること |
| ワークロードが準備完了 | 現在のランタイムと probe の状態 | 新規の認証、正しい外部ルーティング、または有用な機能 |
| 依存先にアドレス可能 | 解決済みのインストールリンク | プロバイダーの認証情報/設定、または要求されたモデル/アクション |
| プロダクトが利用可能 | 公開面への新規接続と、実際の認証済みインタラクション | 未テストのルート、他の環境、または長期的な安定性 |

## 決着は成功ではない

プラットフォームの配送において、**settled** とは、派生したロールアウトが終端結果（Ready、Skipped、または Failed）に到達したことを意味します。これらは個別に数えてください。一致する observed generation と選択されたリリースを伴わない古い Ready ステータスは、新しい配送の証明にはなりません。既存の接続はデータプレーンのリグレッションを覆い隠すことがあるため、手動での読み戻しは、正確な公開面への新規接続を使って行う必要があります。

## Marketplace の condition

`Ready` は投影されたグラフを対象とし、`Healthy` は宣言されたアプリのヘルスレポートを対象とします。セットアップ要件を持つ定義には、`Configured` も付与されます。Ready で Configured が false の場合は `NeedsConfiguration` になります。ヘルスオブザーバーは、意図的に未設定のアプリを probe するのではなく、`Healthy=Unknown/NotConfigured` を報告します。要件を持たない定義には、Configured がまったく存在しなくても構いません。

Unconfigured の依存先でもアドレス可能であり、したがって依存リンクを解決できる場合があります。それは、モデルがプロンプトに応答できることや、アプリがその機能を実行できることの証明にはなりません。

ヘルスの結果は、トランスポート/プロキシの障害（`ServiceUnreachable`）、アプリケーションの非成功（`AppResponded`）、成功レスポンスの形式が不正であること（`InvalidReport`）、および提供中のインカネーションが変化中であること（`Transitioning`）を区別します。プロキシの 401 は、自動的にアプリケーションの認証情報の障害を意味するわけではありません。シークレットをローテーションする前に、失敗している境界を調査してください。

## 釣り合いの取れた受け入れ

コード変更に対しては、影響を受ける契約を露呈させられる最小のチェックを実行してください。目に見える振る舞いに対しては、実際のブラウザ経路を使ってください。永続化に対しては、安全で認可された書き込みを行い、それを読み戻してください。新規ログインは、既に認証済みのセッションとは別に確認してください。

有用なレポートには、意図したソース/イメージ、観測したリリース/generation、正確な対象面、観測期間、アクション、結果、および限界が含まれます。リダイレクトを認証成功に、短い probe を soak テストに、観測していない状態を不在に格上げしないでください。このガイドのリリース `{{.ReleaseVersion}}` が記録しているのは手順であり、ライブの readiness ではありません。
