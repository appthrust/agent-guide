# Project のアプリケーションモデル

| 概念 | 意味 | エージェントの運用ルール |
| --- | --- | --- |
| Project | アプリケーションリソース、権限、コンテキストのスコープ | すべてのリクエストを `{{.ProjectID}}` にバインドしてください。他の環境のコンテキストを再利用しないでください |
| Application | Component、ブランチ、設定、リリースをまとめるプロダクトレベルのグループ | 表示名で同一視せず、ID とオーナーシップを読み取ってください |
| Component | 宣言されたワークロード、データベース、キャッシュ、その他の構成要素 | そのオーナーの入力を変更してください。配送とランタイムは別々に確認してください |
| ApplicationStack | Component、接続、関連リソースの宣言的なグラフ | 子が Stack 管理下にある場合は、これをライフサイクルのオーナーとして扱ってください |
| ComponentConnection | 必要なランタイム設定を投影する宣言された接続 | 生成されたエンドポイントやシークレットをハードコードしないでください |
| Publish | エンドポイントを通じて Application を公開する意図 | ルート、DNS/TLS、認可、実際の公開時の動作を検証してください |
| Release | 選択された不変のランタイム実体とその遷移 | 初期イメージ、ターゲットリリース、安定して提供中のリリースを区別してください |
| Marketplace 定義 | カタログを出所とする署名付きの ApplicationStackDefinition とそのバージョン | カタログへの受け入れがイメージの権限であり、任意のレジストリの内容ではありません |
| AppInstallation | カタログからのインストール、ポリシー、要件、読み取りモデルを記録する Project のレコード | インストールのライフサイクル／依存関係の情報を所有しますが、グラフのすべてのフィールドを所有するわけではありません |
| Operation | 要求された変更に対する受理の通知と観測可能な進捗 | 受理は完了ではなく、完了はプロダクトとしての受け入れではありません |

## 2 つの制御パス

開発者ワークフロー: ソース → イメージの公開 → リポジトリの選択 → リリース → ランタイム → 公開されたプロダクトの動作。

Marketplace ワークフロー: アプリのパブリッシャー → 署名付きカタログ → 検証済みのカタログソース → 定義 → インストールと Stack → 受け入れ済みイメージ → リリース。Platform のリリースと Marketplace アプリのリリースは独立しています。一方を更新しても、もう一方が変更されたことの証明にはなりません。

Marketplace のグラフは Platform API を通じてユーザーが所有します。インストールコントローラーは、その依存関係の接続と受け入れ済みイメージのセットに加え、リンク、ヘルス、利用可能なバージョンなどのステータスを管理します。ユーザーが削除した依存関係を暗黙に再作成したり、編集されたグラフのメンバーをすべて修復したりはしません。

## 正しいオーナーをたどる

アプリの概要には `apth apps get`、Stack ID の確認には `apth application-stacks list`、Component ID の確認には `apth components list` を使ってください（完全な呼び出し構文はクックブックを参照してください）。固定された CLI にコマンドがない場合は、Marketplace のインストールのライフサイクルを Dashboard で管理してください。

廃止された addon の用語を、2 つ目のオーナーシップモデルとして復活させないでください。Component の受理された意図、準備完了のリンク、設定済みのプロバイダー、動作するユーザー操作は、関連してはいますが別々の事実です。
