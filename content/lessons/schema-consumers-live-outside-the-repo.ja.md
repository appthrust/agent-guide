# スキーマの利用者はリポジトリの外にいる

## 過去の観察事項

あるカタログがネストされたヘルスプローブの値を提供していた一方で、`web-service` はフラットなキーを読み取っていました。意図したヘルスエンドポイントは、実際のワークロードのプローブにはなっていませんでした。その後、ネストされたキーを拒否するようにしたところ、別の問題が明らかになりました。既存の保存済みの値と配布済みのカタログが、拒否された形のままだったのです。一部の安定したワークロードは正常なままでしたが、現在のグラフは Degraded になりました。

このインシデントの最終的なソース上の解決策として、検証の前に適用される移行と、カタログ/リリース選択時の互換性チェックが導入されました。それ以前に行われた一時的なライブ修復は、プロジェクションを編集してよいという一般的な許可ではありません。

## 再利用可能なルール

スキーマの利用者には、現在のリポジトリのフィクスチャだけでなく、公開済みのアーティファクト、永続化された Application の値、稼働中のレンダラーも含まれます。同じ値を、プロデューサー → 署名・配布済みカタログ → インストールグラフ → Component レンダラー → 実際のプローブ、という経路で通してテストしてください。フィクスチャが正しくても、配布されたアーティファクトが正しいことの証明にはなりません。

`web-service` の場合、該当するフラットなキーは `readinessProbePath` と `livenessProbePath` です。似た綴りのネストされたオブジェクトが受け入れられると想定しないでください。権限のある移行を行う際は、無関係な値と所有ラベルをすべて保持してください。

## エージェントの対応

グラフが検証/レンダリングの失敗を報告した場合は、正確なスキーマ上の理由と現在の generation を確認してください。近くに見える症状だけから、キャパシティ、不正なヘルスエンドポイント、アプリケーションのクラッシュと診断しないでください。`ExitCode0` だけでは根本原因になりません。

プロデューサーとコンシューマーの不一致は、秘匿化した入力の形、スキーマの識別情報、実際にレンダリングされたプローブ、変更前後の観察結果を添えてエスカレーションしてください。古いカタログの値を正常に見せるために、検証を弱めたり互換性のためのフォールバックを追加したりしないでください。
