# タイムアウトに必要なのは時間の延長ではなく原因の特定

## 過去の観察

開発スループットのレビューにより、CI が遅いと感じられる原因の多くは、コンパイルの遅さではなく、放置されたまま停滞したロールアウトやチェックアウトの競合であることがわかりました。いくつかのタイムアウト失敗はそれぞれ担当が異なっていました。コントローラーの順序付け、証明の分類、ブリッジの計画、そして隠れたラッパーのエラーです。すべてのタイムアウトを延ばしていれば、これらの欠陥は残ったままになっていたでしょう。

## 再利用可能なルール

各ステージを個別に計測してください: リクエスト／CI ゲート → アーティファクトの公開 → 選択 → ロールアウトの収束 → プロダクトのプローブ。対象となる選択そのものの進行理由を保持してください。下位レベルの Application が正常であっても、上位レベルの選択が収束していないことはあり得ます。

型付きのリトライ契約の適用範囲は狭いものです。一時的であるとわかっている競合であれば、回数を限定した再実行が正当化される場合があります。一方、別の 409 は、所有権／受け入れに関する終端的な拒否である可能性があります。SDK が `delivery_pending` を処理しているからといって、`delivery_blocked` やあらゆる Marketplace エラーをリトライしてよいことにはなりません。

## エージェントの対応

期限に達したら、最後の状態、リリース／Operation の識別子、経過時間の範囲、満たされていない述語を記録してください。時間を延ばす前に、担当側のエラーを確認してください。診断情報が取得できていなかった場合は、推測でリトライによる修正を行うのではなく、次の試行で、許可された範囲内の最小限かつ限定的な観測を追加してください。

アプリケーション開発では、独立した実装作業をプロビジョニングと並行して進めてかまいませんが、プロビジョニングの結果は把握できる状態にしておいてください。失敗した Operation をデタッチされたループの中に隠さないでください。後の独立した観測で進行が確認されたとしても、タイムアウトはタイムアウトとして報告してください。

過去の開発チャネルにおける置き換えポリシーは、運用者に対する普遍的な許可ではありません。この Project のアプリタスクは、リリースチャネルを変更したり、その所有者を迂回したりすることはできません。
